1. システム概要

1.1 システム名（仮）
	•	ラーメン評価プラットフォーム（仮称：朝ラー戦果 / RAMEN-OS など）
	•	目的：
	•	ラーメン店の情報・レビュー・評価を一元管理するデータベースサイト
	•	従来の点数だけのランキングではなく、レビュアの質・店の文脈・カテゴリ特性を考慮した “信頼できる評価” を提供する

1.2 コンセプト
	•	「ラーメンデータベース（ramendb.supleks.jp）に近い機能＋あなた独自の評価ロジック」
	•	特徴：
	•	10点満点評価
	•	レビュアーの信頼スコア（重み付け）
	•	店ごとのカテゴリ・世界観に基づいた評価軸
	•	朝ラー／中高年向け／健康寄りなどの軸もタグ／スコアとして扱う

1.3 対象ユーザー
	•	一般のラーメン好き・食べ歩き勢
	•	ラーメン店主・飲食事業者
	•	あなた自身（データ活用・出店戦略・商品開発のインプット）

⸻

2. ユースケース（主要な使い方）

2.1 一般ユーザー
	•	店を検索する
	•	エリア／路線／駅／住所
	•	ラーメンの種類（家系・二郎系・味噌・ラーショ系・朝ラーなど）
	•	スコア順／レビュー数順／新着順
	•	店詳細ページを見る
	•	店の基本情報（住所／営業時間／定休日／席数／駐車場など）
	•	写真（外観・内観・ラーメン）
	•	総合スコア（10点満点）
	•	レビュー一覧
	•	自分でレビューを書く
	•	総合点（0〜10点）
	•	コメント（テキスト）
	•	写真アップロード

2.2 レビュアー（登録ユーザー）
	•	マイページで自分のレビュー履歴を閲覧
	•	自分の「レビュアースコア」（信頼度）を確認（★将来機能）
	•	記事依頼・アマギフ連携（★将来機能）

2.3 管理者（あなた／運営）
	•	店舗情報の登録・編集・削除
	•	レビューのモデレーション（通報対応・削除・非表示）
	•	レビュアースコア算出ロジックの管理
	•	アマギフ配布状況の管理（★後で）

⸻

3. 機能要件（MVP）

3.1 店舗管理機能

3.1.1 店舗基本情報
	•	店名
	•	フリガナ
	•	カテゴリ
	•	複数タグ（家系・二郎系・味噌・ラーショ・朝ラー・健康志向等）
	•	住所・緯度経度
	•	最寄駅・路線
	•	電話番号
	•	営業時間（複数スロット）
	•	定休日
	•	席数（カウンター／テーブル）
	•	駐車場有無／台数
	•	公式サイト・X・Instagram 等のリンク
	•	備考・こだわり

3.1.2 店舗プロファイル（評価基準情報）★あなた独自
	•	店の「世界観」テキスト（例：昭和ラーショ進化系、朝ラー特化、中高年向け等）
	•	評価重みのプロファイル（将来のAI補正用）
	•	スープ重視度
	•	麺重視度
	•	具材重視度
	•	コスパ重視度
	•	胃に優しい度重視
	•	朝ラー適性重視
	•	管理画面で編集できるようにする（最初はあなたが手で入れる前提）

⸻

3.2 レビュー機能

3.2.1 レビュー投稿
	•	対象店舗ID
	•	総合スコア（0.0〜10.0／0.5刻み or 0.1刻みは要検討）
	•	コメント本文
	•	来店日（任意）
	•	写真アップロード（数枚まで）
	•	レビュアーID（匿名投稿可／将来的に会員制へ拡張）

3.2.2 レビュー表示
	•	店ページにレビュー一覧（新着順／スコア順）
	•	各レビューの要素：
	•	ニックネーム
	•	スコア
	•	投稿日
	•	コメント
	•	写真
	•	（将来）レビュアースコア（例：信頼度★4.3）

⸻

3.3 スコアリング・ランキング

3.3.1 店舗スコア（MVP版）
	•	単純に 平均値 からスタート（実装が簡単なため）
	•	店スコア = 全レビューの平均（総合点）
	•	レビュー件数表示
	•	将来：重み付き平均に差し替え可能な設計にしておく
	•	店スコア = Σ(レビュースコア × レビュアー重み) / Σ(レビュアー重み)

3.3.2 ランキング
	•	エリア別ランキング
	•	カテゴリ別ランキング（家系、二郎系、朝ラー等）
	•	ソート条件：
	•	総合スコア
	•	レビュー数
	•	新着レビューの有無（最近動きがある店）

⸻

3.4 検索・ナビゲーション
	•	店名検索
	•	エリア／駅／路線検索
	•	カテゴリ絞り込み（家系／朝ラー／中高年向け etc.）
	•	絞り込み条件：
	•	営業時間帯（例：6〜10時に営業している → 朝ラー絞り込み）
	•	予算（ラーメン1杯の価格帯：〜800円、800〜1,000円、1,000円〜等）
	•	駐車場あり／なし

⸻

3.5 管理者機能（最低限）
	•	ログイン（管理者用）
	•	店舗一覧・検索・編集
	•	レビュー一覧・検索・削除／非表示
	•	ユーザー一覧（後で実装）

⸻

4. 将来拡張（あなたの本命機能）

ここは最初から設計だけ意識しておくエリア。

4.1 レビュアー信頼スコア
	•	各レビュアーに reviewer_weight (0.0〜1.0) を付与
	•	算出ロジック（例）：
	•	他のレビュアーとのスコア整合性
	•	店の最終評価との乖離度
	•	レビュー数・文章量
	•	写真の有無
	•	結果：
	•	良質なレビュアーの点数の重みが高くなる
	•	自作自演／荒らしレビューの影響は小さくできる

4.2 AIによるレビュー解析
	•	レビュー本文をNLP解析し、構造化情報を自動抽出：
	•	味の傾向（濃い／あっさり／魚介強め／動物系強め）
	•	油の量
	•	塩分きつめ／控えめ
	•	胃もたれしやすい／しない
	•	朝ラー向き／向かない
	•	これを店プロファイルに反映し、検索条件として使う

4.3 ライター報酬・アマギフ連携
	•	レビュー（記事）を投稿 → AIが品質判定 → スコアに応じてアマギフ付与
	•	例：
	•	Aランク記事：1,000円
	•	Bランク：500円
	•	Cランク：300円
	•	ライター募集ページ
	•	報酬履歴の管理画面（運営／本人）

⸻

5. 非機能要件（ざっくり素案）

5.1 パフォーマンス
	•	店舗数：当初 〜数千件を想定（将来数万件）
	•	レビュー数：年間 1,000〜数万件
	•	レスポンス：
	•	検索・一覧：1〜2秒以内を目標
	•	店詳細：2秒以内

5.2 セキュリティ
	•	管理画面はID/パスワード＋二段階認証（将来）
	•	画像アップロードの拡張子・サイズ制限
	•	XSS・CSRF対策

5.3 SEO
	•	店舗ごとに固有URL（/shops/{id} or /ramen/{slug}）
	•	メタタグ・OGP対応
	•	パンくずリスト（エリア／カテゴリなど）
