## 1. 基本コンセプト

### 1.1 コアアイデア

**「ユーザー登録のハードルを極限まで下げつつ、パーソナライズと質の高いレビューを実現する」**

RamenDBは、一般的なレビューサイトとは異なるアプローチを取る。ユーザーに登録を強制せず、閲覧・検索は完全に自由とする。しかし、裏側では匿名のまま行動データを蓄積し、パーソナライズされた推薦を提供する。レビュー投稿という「コミットメントの高いアクション」を取る時のみ、簡単なOAuth認証を求める。

### 1.2 設計思想

#### ユーザー体験重視
- 初回訪問時に登録を求めない
- 閲覧・検索は完全にオープン
- パーソナライズ機能も登録不要で提供
- 必要な時だけワンクリックでログイン

#### データ品質の担保
- レビュー投稿は認証必須（スパム・自作自演防止）
- 匿名でも行動履歴を蓄積（パーソナライズ精度向上）
- レビュアー信頼度の算出が可能な設計

#### 段階的なエンゲージメント
- Phase 0: 完全匿名（閲覧のみ）
- Phase 1: 匿名ID自動付与（パーソナライズ開始）
- Phase 2: OAuth認証（レビュー投稿可能）
- Phase 3: 継続利用（マイページ、お気に入り等）

## 2. 機能とユーザー識別の関係

### 2.1 ユーザー識別が不要な機能

以下の機能は完全にオープンで、ユーザー登録・ログインなしで利用可能：

- **店舗検索**
  - キーワード検索
  - カテゴリ検索
  - エリア/駅/路線検索
  - 都道府県検索
  - 詳細フィルタリング

- **店舗情報の閲覧**
  - 店舗詳細ページ
  - 基本情報（住所、営業時間等）
  - レビュー一覧の閲覧
  - 写真ギャラリー
  - 地図表示

- **ランキング・一覧**
  - スコア順ランキング
  - カテゴリ別ランキング
  - 新着レビュー

### 2.2 匿名ID（自動付与）が必要な機能

ユーザーは意識しないが、裏側で匿名IDを自動生成・付与して実現：

- **パーソナライズ推薦**
  - 「あなたへのおすすめ」表示
  - 閲覧履歴に基づく推薦
  - 検索履歴に基づく推薦
  - 好みの傾向分析

- **行動履歴の記録**
  - 閲覧した店舗
  - 検索キーワード
  - よく見るカテゴリ
  - アクセスパターン

**実装方法**:
- LocalStorage に UUID を自動生成・保存
- Cookie にも保存（バックアップ）
- サーバー側でuser_activitiesテーブルに記録
- ユーザーには完全に透明（気づかない）

### 2.3 OAuth認証が必須な機能

以下の機能は、OAuth認証（Google または X）が必須：

- **レビュー投稿**
  - 新規レビュー投稿
  - レビュー編集
  - レビュー削除
  - 画像アップロード

- **マイページ機能**（将来実装）
  - プロフィール表示・編集
  - 投稿したレビュー一覧
  - お気に入り店舗
  - フォロー/フォロワー

- **インタラクション機能**（将来実装）
  - レビューへのいいね
  - コメント投稿
  - 通知機能

**認証タイミング**:
- レビュー投稿ボタンをクリックした時
- マイページにアクセスした時
- その他認証が必要な機能を使おうとした時

**認証方法**:
- Google OAuth（推奨）
- X (Twitter) OAuth
- ワンクリックで簡単ログイン
- メールアドレス・パスワード不要

```

↓

↓

↓

// バックエンドにユーザーレコード作成

{
  anonymous_id: "uuid-xxxx-xxxx-xxxx",
  created_at: "2025-11-27T12:00:00Z"
}
```

- 閲覧した店舗（restaurant_id）

- 選択したカテゴリ（category_slug）
- アクセスした駅/路線（station, railway）
- 滞在時間
- クリックしたボタン

**ユーザー体験**:
- 引き続き何の制約もない
- 「あなたへのおすすめ」セクションが表示される

## 4. OAuth プロバイダーの統合

### 4.1 複数プロバイダーの扱い

**問題**:
同一ユーザーが Google と X の両方でログインすると、別々のアカウントになってしまう可能性がある。

**解決策（Supabase Authを使用）**:

Supabase Authは自動的にメールアドレスで名寄せを行う：

```
1. Google でログイン
   → auth.users テーブルにユーザー作成
   → auth.identities に Google の情報を記録

2. 後日、同じメールアドレスで X でログイン
   → 既存の auth.users を検出
   → auth.identities に X の情報を追加
   → 1つの auth.users に複数の identities が紐付く
```

**データ構造**:
```sql
-- Supabase Auth が自動管理
auth.users (
  id: "123e4567-...",
  email: "user@gmail.com",
  ...
)

auth.identities (
  -- Google の情報
  user_id: "123e4567-...",
  provider: "google",
  provider_id: "108012345..."

  -- X の情報
  user_id: "123e4567-...",  -- 同じ user_id
  provider: "twitter",
  provider_id: "1234567890"
)
```

### 4.2 注意点

**Xはメールアドレスを返さない場合がある**:
- X の OAuth でメールアドレスが取得できない場合
- 自動統合ができない
- マイページで「アカウント連携」機能を提供

**メールアドレスを変更した場合**:
- 各プロバイダーで異なるメールアドレスを使うと別アカウント扱い
- これはユーザーの意図的な使い分けの可能性もあるため許容

## 5. データベース設計（概要）

### 5.1 users テーブル

```sql
CREATE TABLE users (
  -- 主キー
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

  -- OAuth認証情報（レビュー投稿者のみ持つ）
  auth_user_id UUID UNIQUE,  -- Supabase Auth の users.id
  email TEXT,
  username TEXT UNIQUE,
  display_name TEXT,
  avatar_url TEXT,

  -- 匿名ユーザー情報（全員持つ）
  anonymous_id TEXT UNIQUE,  -- LocalStorage の UUID

  -- ユーザープロファイル（趣味嗜好）
  favorite_categories JSONB,  -- ['iekei', 'jiro', 'miso']
  favorite_stations TEXT[],   -- ['渋谷', '新宿', '池袋']
  preference_weights JSONB,   -- {taste: 5, price: 3, service: 2}

  -- 統計情報
  review_count INTEGER DEFAULT 0,
  reviewer_score NUMERIC(3,2) DEFAULT 0.5,  -- レビュアー信頼度

  -- タイムスタンプ
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- インデックス
CREATE INDEX idx_users_auth ON users(auth_user_id);
CREATE INDEX idx_users_anonymous ON users(anonymous_id);
CREATE INDEX idx_users_username ON users(username);
```

**ポイント**:
- `auth_user_id` は NULL 可（匿名ユーザーは NULL）
- `anonymous_id` は必須（全員持つ）
- OAuth認証後も `anonymous_id` は保持（データ統合の追跡用）

### 5.2 user_activities テーブル

```sql
CREATE TABLE user_activities (
  -- 主キー
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

  -- ユーザー紐付け
  user_id UUID REFERENCES users(id) ON DELETE CASCADE,

  -- アクティビティ情報
  activity_type TEXT NOT NULL,  -- 'view' | 'search' | 'click' | 'favorite'

  -- 対象情報
  restaurant_id UUID REFERENCES restaurants(id) ON DELETE SET NULL,
  category_slug TEXT,
  station TEXT,
  railway TEXT,
  prefecture TEXT,
  search_query TEXT,

  -- その他のメタデータ
  metadata JSONB,  -- 柔軟に追加情報を格納

  -- タイムスタンプ
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- インデックス
CREATE INDEX idx_activities_user ON user_activities(user_id);
CREATE INDEX idx_activities_type ON user_activities(activity_type);
CREATE INDEX idx_activities_restaurant ON user_activities(restaurant_id);
CREATE INDEX idx_activities_created ON user_activities(created_at DESC);
```

**記録される行動の例**:
```javascript
// 店舗詳細を閲覧
{
  user_id: "uuid-xxxx",
  activity_type: "view",
  restaurant_id: "restaurant-uuid",
  metadata: {
    duration_seconds: 45,
    scrolled_to_reviews: true
  }
}

// 検索
{
  user_id: "uuid-xxxx",
  activity_type: "search",
  category_slug: "iekei",
  station: "渋谷",
  search_query: "家系 渋谷",
  metadata: {
    result_count: 12
  }
}

// お気に入り追加（将来）
{
  user_id: "uuid-xxxx",
  activity_type: "favorite",
  restaurant_id: "restaurant-uuid"
}
```

## 6. パーソナライズアルゴリズム（概要）

### 6.1 推薦の基本ロジック

**入力データ**:
- ユーザーの閲覧履歴（user_activities）
- ユーザーの検索履歴（user_activities）
- ユーザーが高評価したレビュー（reviews）
- ユーザーのプロファイル（favorite_categories, favorite_stations）

**推薦アルゴリズム**:

1. **コンテンツベースフィルタリング**
   - よく見るカテゴリの店舗を推薦
   - よく検索する駅周辺の店舗を推薦
   - 高評価したレビューと似た特徴の店舗を推薦

2. **協調フィルタリング**（将来実装）
   - 似た行動パターンのユーザーを検出
   - そのユーザーが高評価した店舗を推薦

3. **ハイブリッド**
   - 上記を組み合わせてスコアリング
   - 新規性・多様性も考慮

### 6.2 実装イメージ

```sql
-- パーソナライズ推薦クエリの例
WITH user_preferences AS (
  -- ユーザーがよく見るカテゴリ
  SELECT category_slug, COUNT(*) as view_count
  FROM user_activities
  WHERE user_id = :user_id
    AND activity_type = 'view'
    AND category_slug IS NOT NULL
  GROUP BY category_slug
  ORDER BY view_count DESC
  LIMIT 3
),
user_stations AS (
  -- ユーザーがよく見る駅
  SELECT station, COUNT(*) as search_count
  FROM user_activities
  WHERE user_id = :user_id
    AND activity_type = 'search'
    AND station IS NOT NULL
  GROUP BY station
  ORDER BY search_count DESC
  LIMIT 3
)
SELECT r.*,
  -- スコアリング
  (
    -- カテゴリマッチ
    CASE WHEN rc.category_slug IN (SELECT category_slug FROM user_preferences)
         THEN 10 ELSE 0 END
    +
    -- 駅マッチ
    CASE WHEN r.nearest_station IN (SELECT station FROM user_stations)
         THEN 5 ELSE 0 END
    +
    -- 平均スコア
    r.average_score
  ) AS recommendation_score
FROM restaurants r
LEFT JOIN restaurant_categories rc ON r.id = rc.restaurant_id
WHERE r.id NOT IN (
  -- 既に見た店舗は除外
  SELECT restaurant_id FROM user_activities
  WHERE user_id = :user_id AND activity_type = 'view'
)
ORDER BY recommendation_score DESC
LIMIT 10;
```

## 8. セキュリティ・プライバシー考慮事項

### 8.1 匿名ユーザーのプライバシー

**記録するデータ**:
- 閲覧した店舗ID
- 検索キーワード
- 選択したカテゴリ・駅

**記録しないデータ**:
- IPアドレス（ログには残るが、user_activitiesには保存しない）
- ブラウザフィンガープリント
- 位置情報（GPS）

**データ保持期間**:
- 匿名ユーザーの行動履歴: 90日間
- 認証ユーザーの行動履歴: 無期限（ユーザーが削除可能）

### 8.2 OAuth認証のセキュリティ

**Supabase Auth の機能を使用**:
- PKCE (Proof Key for Code Exchange) 対応
- CSRF トークン検証
- セッション管理（JWT）

**実装上の注意**:
- OAuth コールバックURLのホワイトリスト化
- State パラメータの検証
- アクセストークンの安全な保管

### 8.3 データ削除・エクスポート

**ユーザーの権利**:
- 自分の全データを閲覧できる
- 自分のアカウントを削除できる
- データをエクスポートできる（将来実装）

**削除時の動作**:
```sql
-- ユーザー削除時
DELETE FROM users WHERE id = :user_id;
-- CASCADE で以下も削除される
-- - user_activities
-- - reviews（著作権的に削除すべきか要検討）
```

### 9.1 要件定義フェーズで詰めるべき項目

1. **匿名ユーザーの行動記録範囲**
   - どこまで記録するか（プライバシーとの兼ね合い）
   - データ保持期間（GDPR等の法規制を考慮）

2. **レビュー投稿の制限**
   - 1ユーザー・1店舗あたりのレビュー数制限
   - 連続投稿の制限（スパム対策）
   - レビュー編集・削除のルール

3. **パーソナライズアルゴリズムの精度**
   - 最低限必要な行動データ数
   - 推薦の多様性（同じ店ばかり出さない）
   - 新規店舗の露出機会

4. **OAuth プロバイダーの選定**
   - Google と X 以外のプロバイダーを追加するか
   - メールアドレス認証も提供するか

5. **匿名データ統合のタイミング**
   - ログイン時に自動統合で良いか
   - ユーザーに選択肢を与えるか

### 9.2 技術的な詳細設計が必要な項目

1. **LocalStorage のフォールバック**
   - Cookie が無効な場合の対応
   - シークレットモードでの動作

2. **パフォーマンス**
   - user_activities の肥大化対策
   - 推薦クエリの最適化
   - キャッシュ戦略

3. **バックアップ・復元**
   - 匿名データの統合失敗時の対応
   - データの整合性チェック

4. **監視・分析**
   - 匿名ユーザー→認証ユーザーの転換率
   - パーソナライズの効果測定
   - エラー検知

## 10. まとめ

### 10.1 このコンセプトの強み

1. **ユーザーフレンドリー**
   - 登録の壁がない
   - すぐに使い始められる
   - 必要な時だけ簡単ログイン

- スケーラブルなアーキテクチャ
