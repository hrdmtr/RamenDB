対象: ラーメン検索・レビューサイト MVP  
目的: ユーザーが「自分の知りたい観点」で絞り込みできる、直感的で高速な検索UIを提供する。

---

## 1. 概要
本検索UIは、SUUMO（不動産検索）のUIパターンを参考に、  
ラーメン店舗を多軸で絞り込み可能な **「ボタン式 × タグ式 × スライダー式 × マップ連動式」** を特徴とする検索画面を提供する。

目的は、  
ユーザーが **大量の店舗を “自分の感性基準” で素早く選別できる検索体験** を実現すること。

## 4. 条件詳細パネル（UI仕様）
SUUMO のように「パネルが階層的に開いて条件を細かく選択できる」方式。

### 4.1 要件
- 条件カテゴリをクリックするとモーダル or スライドアップパネルが開く  
- 項目はカテゴリ別に **チェック式 / スライダー式 / トグル式**  
- 「この条件で検索」ボタンで閉じて結果画面へ反映  
- 選択された条件はタグとしてヘッダー下に並ぶ（SUUMO式）
- タグは × で個別削除可能  
- 「条件を全てクリア」ボタンあり

## 10. 実装仕様Q&A（確定版）

以下は実装前に確認した設計判断の記録。

### Q1: 価格帯のデータはどう持つ？

**結論**: `restaurants.price_range` を追加する一択。

**理由**:
- 価格帯は「店舗固有の基本属性」であり、レビュー依存にしてはならない
- 店舗オーナーが自分で設定すべき一次情報
- SUUMOライクの検索では「絞り込み項目は必ず固定属性」であるべき
- 価格帯はレビューと混ぜると壊れる（レビュアーの主観＝不正確）

**実装**:
```sql
price_range: ENUM('~700', '700-900', '900-1200', '1200~')
```

---

### Q2: 朝ラー判定は？ 営業時間から自動計算？ それともフラグ？

**結論**: 別フラグを持つ。

**理由**:
- 営業時間だけで「朝ラー文化の意図」が判別できない
- 朝営業してるだけの店と、朝ラーに本気の店は全く違う
- 朝から営業していても、朝ラー文化に対応していない店舗も多い

**実装**:
```sql
is_morning_ramen: BOOLEAN DEFAULT FALSE
```

---

### Q3: 店舗特徴は別テーブル？ それともJSON？

**結論**: `restaurant_features` テーブルを作る（正規化）。

**理由**:
- SUUMOライク検索では「複数選択フィルタ」を高速に行う必要がある
- JSON 検索は重くなる
- 将来の拡張で柔軟性が高い
- 特徴の種類が増える前提だから正規化が最適

**実装**:
```sql
-- 特徴マスタテーブル
CREATE TABLE features (
  id UUID PRIMARY KEY,
  name VARCHAR(100) NOT NULL,
  category VARCHAR(50)
);

-- 店舗-特徴 中間テーブル
CREATE TABLE restaurant_features (
  id UUID PRIMARY KEY,
  restaurant_id UUID REFERENCES restaurants(id),
  feature_id UUID REFERENCES features(id),
  UNIQUE(restaurant_id, feature_id)
);
```

---

### Q4: あっさり〜こってりスライダーは店の固定値？レビュー平均？

**結論**: レビュー平均値を使用。

**理由**:
- 本サイトは「レビュアーの感性を基準に検索できる」目的なので、レビュー平均の方が適合性が高い
- 固定値では「店主の主観」になって意味が薄い
- レビュー基準だからこそ「レビュアーの感性」が検索できる
- やりたい「レビュアー軸の信頼度算出」と相性が良い

**実装**:
```sql
-- reviewsテーブルに追加
flavor_richness: INTEGER (0-10)  -- 0: あっさり 〜 10: こってり

-- restaurantsテーブルには平均値をキャッシュ（高速化）
avg_flavor_richness: DECIMAL(3,1)

-- トリガーでレビュー投稿/更新時に自動計算
```

---

### Q5: 実装優先順位

**確定順序**:
1. 味・ジャンル（既存カテゴリ活用）
2. 価格帯
3. 時間帯（朝ラー対応含む）
4. 店舗特徴（券売機/駐車場など）
5. 並び替え（近い順 / コスパ順 / 人気順）

**意図**: 味・価格・時間・特徴の4本柱でSUUMOの構造と完全一致させる。

---

### Q6: UI形式（モーダル vs スライドアップパネル）

**結論**: 両方対応（スマホ＝スライドアップ、PC＝ドロップダウン）。ただし、実装優先はスマホ。

**理由**:
- ラーメン検索は8割スマホ（Googleアナリティクスで飲食店検索はモバイル80%）
- SUUMOを参考にするなら
  - スマホ＝下からスライドアップ（重要度高）
  - PC＝ドロップダウン（後回しでOK）
- 実装コスト：
  - スマホ版スライドアップパネルは1実装で済む
  - PCドロップダウンはスマホの流用が難しい → 後回しが合理的

**MVP最終決定案**:
- **MVP**: スマホ Only（スライドアップパネル）
- **PC**: 検索条件を横に出す簡易UIでいい
- SUUMO完全模倣は後で良い

---

### Q7: GPS機能（現在地から近い順）

**結論**: MVPでは後回し。

**理由**:
- GPSは工数が重い（精度調整、権限、クロスブラウザ問題）
- 緯度経度のDB追加は簡単だが、GPS検索ロジックのテストが重い
- MVPの目的は「情報整理されたラーメン検索」であり、機能的価値より品質の高い口コミの方が重要

**MVP最終決定案**:
- **MVP**: GPS検索なし、駅名・市区町村絞り込みのみ
- **第2フェーズ**: GPS / 現在地から近い順（ニーズ大なので将来必須）

**実装準備**:
```sql
-- 将来のGPS機能のために先に追加しておく
latitude: DECIMAL(10, 8),
longitude: DECIMAL(11, 8)
```

---

### Q8: サムネイル画像

**結論**: `thumbnail_url` を restaurants に追加。

**理由**:
- 店舗カードは必ず「安定した見た目」が必要
- レビュー依存にすると、以下の問題が出る：
  - レビューに画像がない店舗は空になる
  - 写真の質に大差があり、ブランド毀損
  - 悪意ある写真投稿リスク
- まずは店舗公式 or 自社で撮影した写真をセット
- 後で「レビュー写真のうち評価の高いものをAIで自動判定」など高度化可能

**MVP最終決定案**:
- `restaurants.thumbnail_url`（必須）を追加してMVPはこれで統一
- 自動選択は後にAI加点として実装

**実装**:
```sql
thumbnail_url: TEXT NOT NULL
```

---

### Q9: 検索ボタンの動作

**結論**: 「この条件で検索」ボタン押下時のみ更新。

**理由**:
- SUUMOも本質はボタン押下系（リアルタイムはUIの見せ方）
- リアルタイム検索は：
  - パフォーマンス負荷大
  - 検索条件が複雑な時バグが出やすい
  - UXも落ちる（思わぬフィルタがすぐ走る）
- まずは「この条件で検索」ボタン
- 後で非同期検索にするのは簡単

**実装**:
- 条件変更は内部状態として保持
- 「この条件で検索」ボタンクリック時にAPIコール
- URLクエリパラメータに検索条件を反映（共有可能に）

```sql
price_range VARCHAR(20) CHECK (price_range IN ('~700', '700-900', '900-1200', '1200~'))

```

### reviews テーブル追加フィールド
```sql

```

### 新規テーブル
```sql
-- 店舗特徴マスタ
CREATE TABLE features (
  id UUID PRIMARY KEY,
  name VARCHAR(100) NOT NULL UNIQUE,
  category VARCHAR(50),
  description TEXT
);

-- 店舗-特徴 中間テーブル
CREATE TABLE restaurant_features (
  id UUID PRIMARY KEY,
  restaurant_id UUID REFERENCES restaurants(id) ON DELETE CASCADE,
  feature_id UUID REFERENCES features(id) ON DELETE CASCADE,
  UNIQUE(restaurant_id, feature_id)
);
```
