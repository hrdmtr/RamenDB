## 要件1: レビュー報酬システム（Amazonギフト券配布機能）

### 背景・目的
レビュー数を爆発的に増やすため、Amazonギフト券による報酬システムを構築する。

### 基本方針
- **対象期間**: 一定期間（キャンペーン形式）
- **対象レビュー**: 期間中の全レビュー
- **報酬**: Amazonギフト券（例: 300円）
- **品質管理**: LLMによる自動精査で一定基準以上のレビューのみ報酬付与

---

### 機能概要

#### 1. Amazonギフト券管理機能

**方式**:
- 事前に購入したAmazonギフト券のURLを手動で登録
- 1つずつ消費していく方式

**データ構造**:
```
gift_codes テーブル
- id: ギフトコードID
- url: AmazonギフトURL（暗号化保存）
- label: ラベル（例: "300円", "500円"）
- is_used: 使用済みフラグ
- used_at: 使用日時
- used_by_user_id: 使用者
- created_at: 登録日時
```

**必要な機能**:
- [ ] 管理画面でギフト券URL登録
- [ ] ラベル設定（金額識別用）
- [ ] 在庫状況の確認
- [ ] 在庫アラート機能（残数が少なくなったら通知）

---

#### 2. レビュー品質管理機能（LLM精査）

**目的**:
一定基準以上のレビューのみに報酬を付与し、品質を担保する。

**フロー**:
1. ユーザーがレビューを投稿
2. LLMが自動で内容を精査
3. 基準以上 → 承認 → 報酬付与
4. 基準以下 → 改善指示 → 再提出を促す

**精査項目（検討中）**:
- [ ] 文字数の適切性
- [ ] 具体性・詳細さ
- [ ] 5軸評価との整合性
- [ ] 誹謗中傷・不適切表現のチェック
- [ ] その他（次回詰める）

**データ構造**:
```
review_quality_checks テーブル
- id
- review_id: レビューID
- llm_model: 使用したLLMモデル名
- score: 品質スコア
- status: ステータス（pending/approved/rejected）
- feedback: 改善指示内容
- checked_at: 精査日時
```

**未確定事項**:
- [ ] 使用するLLMモデル（GPT-4, Claude, Gemini など）
- [ ] 具体的な評価基準
- [ ] 改善指示の生成方法（自動 or 手動）
- [ ] 再提出回数の上限
- [ ] 最終判定（自動承認 or 人間による確認）

---

#### 3. 報酬受領機能

**UI仕様**:
- マイページに受領可能なAmazonギフト券の一覧を表示
- 初期状態: URLは非表示
- 「表示」ボタンをクリック → URLまたは「受領済み」を表示
- ボタンクリック時点で受領とみなす

**データ構造**:
```
rewards テーブル
- id
- user_id: ユーザーID
- review_id: レビューID
- gift_code_id: ギフトコードID
- status: ステータス（pending/claimed）
- claimed_at: 受領日時
- created_at: 報酬付与日時
```

**画面イメージ**:
```
マイページ > 報酬一覧

┌─────────────────────────────────────┐
│ Amazonギフト券                       │
├─────────────────────────────────────┤
│ 300円 | 2025-12-01 | [表示]         │
│ 300円 | 2025-12-05 | [表示]         │
│ 300円 | 2025-12-10 | 受領済み       │
└─────────────────────────────────────┘
```

**未確定事項**:
- [ ] 「表示」ボタンを押した後の挙動（一度押したら二度と表示できない？）
- [ ] 受領済み時にURLも表示する？ それとも「受領済み」のみ？
- [ ] ギフト券の有効期限表示の必要性

---

#### 4. 運用フロー（全体）

```
[ユーザー] レビュー投稿
    ↓
[システム] LLMで品質精査
    ↓
    ├─ 基準以下 → 改善指示 → 再提出
    └─ 基準以上 → 承認
         ↓
    [システム] Amazonギフト券を割り当て
         ↓
    [ユーザー] マイページで確認
         ↓
    [ユーザー] 「表示」ボタンクリック
         ↓
    [システム] URL表示 & 受領記録
```

## 要件3: Google Places API を使った店舗自動登録CLIツール

### 背景・目的
Googleマップから店舗情報を効率的に取得し、店舗数を爆発的に増やす。

### 基本方針
- Google Places API（公式）を使用
- コマンドラインツールとして実装
- 地域とキーワードを指定して一括登録
- 見栄えの良い店舗情報（画像付き）を自動収集

---

### 機能概要

#### 1. コマンド仕様

**基本コマンド**:
```bash
npm run scrape-places -- --area="渋谷区" --query="ラーメン"
npm run scrape-places -- --area="新宿区" --query="ラーメン 家系"
```

**引数**:
- `--area`: 地域名（例: 渋谷区、新宿区、港区）
- `--query`: 検索キーワード（例: ラーメン、ラーメン 家系、ラーメン 二郎系）

---

#### 2. Google Places API で取得する情報

**取得対象**:
- 店舗名（必須）
- 住所（必須）
- 緯度経度（必須）
- 電話番号
- 営業時間
- 評価（星の数）
- レビュー数
- 店舗写真（サムネイル用）
- GoogleマップURL
- ウェブサイトURL

**API制限**:
- 無料枠: 月$200分のクレジット（約28,500リクエスト相当）
- 超過分は有料

---

#### 3. データベース登録フロー

**処理ステップ**:
1. コマンドライン引数から地域名とキーワードを取得
2. 地域名から緯度経度を取得（Geocoding API）
3. Places API Nearby Search で店舗を検索
4. 各店舗の詳細情報を取得（Place Details API）
5. データベースに自動登録

**重複チェック**:
- 住所 + 店舗名が一致する場合は上書き更新
- 上書き時はログに記録（後で確認可能）

**ログ出力**:
- 新規登録: 店舗名、住所、登録日時
- 上書き更新: 店舗名、住所、更新日時、更新内容
- エラー: 店舗名、エラー内容

---

#### 4. データベース登録内容

**必須項目** (Places APIから自動取得):
- name: 店舗名
- name_kana: カナ（自動生成 or 空欄）
- address: 住所
- nearest_station: 最寄駅（住所から推定 or 空欄）
- railway: 路線（住所から推定 or 空欄）
- latitude: 緯度
- longitude: 経度

**任意項目** (Places APIから自動取得):
- phone_number: 電話番号
- opening_hours: 営業時間テキスト
- website: ウェブサイトURL
- google_maps_url: GoogleマップURL
- description: 説明（レビュー情報から生成？）
- image_url: 店舗画像（Places APIから取得した写真）

**カテゴリ・タグ**:
- カテゴリ: 任意、複数選択可能（手動設定 or キーワードから自動判定）
- タグ: 任意、複数選択可能（手動設定 or キーワードから自動判定）

---

#### 5. エラーハンドリング

**想定されるエラー**:
- API制限超過 → エラーメッセージを出力して処理停止
- 地域名が見つからない → エラーメッセージを出力
- 店舗情報が不完全 → 警告を出してスキップ or 部分的に登録
- ネットワークエラー → リトライ処理

**リトライ仕様**:
- API呼び出し失敗時は3回までリトライ
- リトライ間隔: 1秒、2秒、4秒（指数バックオフ）

---

### 技術要件

#### 1. Google Places API の設定

**必要なAPI**:
- Places API
- Geocoding API（地域名→緯度経度変換）

**認証方法**:
- API Key を環境変数で管理（`.env.local`）
- `GOOGLE_PLACES_API_KEY=...`

**セキュリティ**:
- API Keyの制限設定（IPアドレス制限、リファラ制限など）
- 本番環境では環境変数で管理

---

#### 2. 実装技術

**使用ライブラリ**:
- `@googlemaps/google-maps-services-js` (公式Node.jsクライアント)
- `commander` or `yargs` (コマンドライン引数パース)
- `chalk` (ログの色付け)
- `dotenv` (環境変数読み込み)

**ファイル構成**:
```
scripts/
  scrape-places.ts         # メインスクリプト
  lib/
    google-places-client.ts # Places API クライアント
    geocoding-client.ts     # Geocoding API クライアント
    db-uploader.ts          # データベース登録処理
    logger.ts               # ログ出力処理
logs/
  scrape-YYYYMMDD-HHMMSS.log # 実行ログ
```

---

### 運用フロー

**基本的な使い方**:
```bash
# 1. 環境変数の設定
echo "GOOGLE_PLACES_API_KEY=your_api_key" >> .env.local

# 2. 渋谷区のラーメン店を一括登録
npm run scrape-places -- --area="渋谷区" --query="ラーメン"

# 3. 新宿区の家系ラーメンを一括登録
npm run scrape-places -- --area="新宿区" --query="ラーメン 家系"

# 4. ログを確認
cat logs/scrape-20251201-120000.log
```

**複数地域を一括処理**:
```bash
# シェルスクリプトで複数地域を処理
for area in "渋谷区" "新宿区" "港区" "品川区"; do
  npm run scrape-places -- --area="$area" --query="ラーメン"
done
```

### 確定事項（実装方針）

1. **必須項目の扱い** ✓
   - `name_kana`, `nearest_station`, `railway` をDBスキーマ上で任意項目に変更
   - Google Places APIでは取得できないため、空欄で登録を許可
   - 理由: MVPでは店舗数を増やすことを優先、後で手動修正可能

2. **店舗画像の扱い** ✓
   - **MVP**: Places APIから取得した画像URLをそのまま保存（案A）
   - **将来**: 画像をダウンロードしてSupabase Storageに保存（案B）に移行
   - 理由: 実装の簡素化、ストレージコスト削減

3. **最寄駅・路線の推定**
   - **MVP**: 任意項目化して空欄で登録
   - **将来**: 駅データベース + 距離計算で自動推定（案2）
   - 実装方法:
     - 駅の緯度経度データベース（オープンデータ）を用意
     - 店舗の緯度経度と各駅の距離を計算
     - 最も近い駅を自動設定
